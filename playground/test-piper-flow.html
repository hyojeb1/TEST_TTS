01

문자열을 UTF-8로 만든다

wmain(argc, argv) → ToUtf8() → std::string

main이 아니라 wmain을 쓴다. 진입점이 wchar_t* argv[]를 주기 때문에 명령줄로 넘긴 한국어가 UTF-16으로 그대로 들어온다. 그 다음 WideCharToMultiByte(CP_UTF8, …)로 UTF-8 바이트열을 만든다.

함정 1 / 3

좁은 문자열 리터럴을 그대로 넘기면 안 된다

piper_synthesize_start는 UTF-8 바이트를 요구한다. 그런데 한국어 로케일 Windows에서 MSVC의 실행 문자셋 기본값은 CP949다. "도네이션…"을 그냥 넘기면 espeak가 해독하지 못한다.

소스 파일 자체도 UTF-8 BOM으로 저장해야 한다. BOM이 없으면 MSVC가 소스를 CP949로 읽어 error C3688: 잘못된 리터럴 접두사 로 컴파일부터 실패한다. 그래서 이 코드는 wide 리터럴 + 명시적 변환이라는 두 단계를 거친다.

02

모델을 메모리에 올린다

piper_create(model_path, config_path, espeak_data_path) → piper_synthesizer*

경로 세 개를 넘기는 단 한 번의 호출이다. 이 안에서 세 가지가 일어난다.

  • .onnx.json을 읽어 sample_rate 22050, espeak.voice "ko", 음소 ID 맵 161개를 세팅
  • espeak_Initialize()로 espeak-ng-data(19 MB, ko_dict 포함) 적재
  • onnxruntime 세션 생성 — libpiper가 SetIntraOpNumThreads(1)로 1코어에 고정

실패하면 예외가 아니라 nullptr을 돌려준다. C API이므로 반환값 검사가 유일한 방어선이다. 측정값은 549 ms — 게임에서는 로딩 화면에서 딱 한 번만 하면 되는 비용이다.

함정 2 / 3

Windows 11은 System32에 낡은 onnxruntime을 갖고 있다

C:\Windows\System32\onnxruntime.dll은 Windows ML용 1.17이다. piper.dll은 ORT API 22(1.22.0)를 요구한다.

DLL 검색 순서상 exe와 같은 폴더가 System32보다 먼저다. 즉 1.22.0을 exe 옆에 복사해두지 않으면 System32 것이 로드되어 The requested API version [22] is not available 로 죽는다. .vcxproj의 PostBuildEvent가 DLL 3개를 $(OutDir)로 복사하는 이유다.

03

합성을 시작한다 — 아직 소리는 없다

piper_default_synthesize_options() → piper_synthesize_start() → PIPER_OK

이 호출은 텍스트를 음소 ID 큐로 바꾸는 것까지만 한다. 신경망은 아직 돌지 않는다.

DLL 안에서 벌어지는 일을 계측해 확인한 결과는 이렇다.

단계결과
espeak_SetVoiceByName"ko" → EE_OK
espeak → IPA 음소dˈoneˌisjʌn ɡˈɐmsɐhˌɐpnidˌɐ
문장 분리2개 (두 번째는 빈 문장)
음소 ID 큐1개 ← 문장 하나당 chunk 하나

큐 길이가 곧 나올 chunk 개수다. 한 문장 = chunk 1개라는 이 사실이 다음 단계의 함정으로 이어진다.

04

chunk를 순회한다 — 이 파일의 핵심

piper_synthesize_next(synth, &chunk) → PIPER_OK | PIPER_DONE | PIPER_ERR_GENERIC

큐에서 문장 하나를 꺼내 onnxruntime을 돌리고 float32 샘플을 채운다. 반환값은 세 가지다.

rc상수실제 의미
0PIPER_OKchunk를 채웠고, 뒤에 더 있다
1PIPER_DONEchunk를 채웠고, 이게 마지막이다
−1PIPER_ERR_GENERIC실패. chunk는 비어 있다

함정 3 / 3 — 가장 오래 걸린 것

PIPER_DONE은 “데이터 없음”이 아니라 “이게 마지막”이다

libpiper의 piper_synthesize_next 마지막 줄은 return chunk->is_last ? PIPER_DONE : PIPER_OK; 다. 마지막 chunk를 PIPER_DONE과 함께 반환한다.

그런데 libpiper README의 공식 예제는 while (next(…) != PIPER_DONE) 로 되어 있어 그 마지막 chunk를 버린다. 문장이 여러 개면 앞부분은 나오니 눈치채기 어렵지만, 문장이 하나뿐이면 유일한 chunk가 곧 마지막이라 오디오가 0바이트가 된다. 증상은 [FAIL] no audio produced 하나뿐이고, 모델 로딩도 음소화도 전부 성공한 상태라 원인이 전혀 드러나지 않는다.

“도네이션 감사합니다” 한 문장을 넣었을 때

그래서 반환값이 아니라 chunk 필드를 기준으로 순회한다. 상류 piper_exe가 src/main/utils/wavfile.cpp에서 쓰는 방식과 같다.

두 가지를 더 챙겨야 한다. chunk.samples가 가리키는 버퍼는 다음 호출에서 재사용되므로 즉시 복사해야 한다. 그리고 TTFA는 루프 시작이 아니라 비어 있지 않은 첫 chunk가 도착한 순간에 찍어야 의미가 있다 — 게임에서 중요한 건 전체 생성 시간이 아니라 말이 언제 시작되느냐다.

05

float32 그대로, 그리고 16-bit WAV로

WriteAll(….raw) → FloatToPcm16() → MakeWavHeader() → WriteAll(….wav)

같은 오디오를 두 형식으로 남긴다. .raw는 libpiper가 준 float32를 손대지 않은 것 — 엔진에 스트리밍으로 밀어넣을 때 쓸 형식이다. .wav는 Windows에서 바로 재생하려고 int16으로 변환하고 44바이트 헤더를 붙인 것이다.

이번 출력의 최고 진폭은 0.4947이라 클리핑이 0%였다. 하지만 libpiper는 정규화를 하지 않는다(Python API의 normalize_audio=True에 해당하는 처리가 없다). 모델이 ±1.0을 넘겨줄 수 있으므로 클램프는 선택이 아니다.

06

측정값을 찍고 끝낸다

piper_free(synth) → printf(…) → return 0

정리는 piper_free(synth) 한 번이다. 이 프로그램은 chunk 루프가 끝난 직후, 파일을 쓰기 전에 해제한다 — 샘플은 이미 pcm 벡터로 복사해뒀으므로 안전하다.

마지막으로 찍는 RTF(Real-Time Factor)가 이 테스트의 결론이다.

참고로 같은 모델을 Python piper-tts로 돌리면 TTFA 43 ms, RTF 0.026으로 C++보다 3배 빠르다. 코드 탓이 아니다. libpiper의 piper.cpp가 onnxruntime 스레드를 intra_op = 1로 하드코딩해 놓았고, C API로는 이 값이 노출되지 않는다. Python 쪽을 같은 intra_op=1로 맞추면 102 ms / RTF 0.059로 같은 수준이 된다.

게임에 붙일 때는 오히려 이 기본값이 유리하다. onnxruntime 기본 설정은 이 머신에서 24코어(시스템 75%)를 순간 점유하는데, 1코어로 묶여 있어도 RTF 0.0765면 충분히 빠르다.

빌드하고 실행하기

1. libpiper를 먼저 빌드한다. espeak-ng는 소스에서, onnxruntime 1.22.0은 자동 다운로드된다. 첫 빌드에 약 5분.

2. 콘솔 프로그램은 Release|x64에서만 TEST_Piper.cpp를 빌드한다. Debug|x64는 기존 TEST_SpeechSynthesis.cpp 그대로다.
